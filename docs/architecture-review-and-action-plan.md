Pattern-Aware SEO Platform — Architecture Review & Action Plan

Source: architecture review conducted in a shared ChatGPT conversation (against the feature/aws-s3-sftp-deploy branch and an uploaded code ZIP), critiqued and turned into an action plan on 2026-09-01. Tech stack recommendation added the same day. Implementation progress (M0, M1, M2) logged 2026-09-01; M3, initial CI verification, a post-M3 hardening pass, the first main promotion, M4 (with a merge-time correction), and M5 all logged 2026-09-02.

Context

The review examined the existing sitemap migration/health-check engine (Next.js frontend, Fastify backend, BullMQ + Redis, PostgreSQL, streaming SAX sitemap parsing, Piscina for CPU-heavy work, S3/SFTP deployment) and concluded the direction is sound: don't rewrite it, evolve it into a pattern-aware, sampling-based SEO intelligence platform that can audit sites with tens or hundreds of millions of URLs without crawling the whole URL universe. The core idea — collapse 90M+ URLs into a few thousand patterns, sample each pattern, verify statistically, and only do targeted deep audits where evidence says to — is the real differentiator and is worth keeping as the north star.

Deployment path: local development on the team's own Mac/Windows PCs first, then deployment to AWS for multi-user access, with model training on the accumulated sampling data planned as a later phase.

Implementation progress
M0 (Phase 0 foundation) — complete. Tooling/enforcement, real workspace packages, packages/shared, initial apps/web scaffold, docs/decisions.md established.
M1 (Phase 1 schema/tenancy) — complete; one correction found post-M3. Core entity model (organization → site → sitemap_run → sitemap_file → pattern → pattern_population / pattern_sample → sample_observation, plus audit_snapshot/sampling_health), degenerate-interval CHECK constraint, compile-time tenant isolation, composite (site_id, id) PKs (ADR-0010). Correction (post-M3, migration 0002): the compile-time query guard was real, but the schema itself allowed a cross-tenant reference — a row could carry one site's site_id while a FK pointed at a different site's parent row, because only the FK column was constrained, not the (site_id, id) pair on the referenced side. Closed via UNIQUE (site_id, id) plus five repointed FKs; isolation.test.ts gained explicit cross-site cases. Two isolation layers — query-time and schema-time — each need their own proof.
M2 (Phase 1 streaming ingestion + pattern extraction) — complete. Single pass over a synthetic 10,000,000-URL corpus: 681 MB peak RSS (1,536 MB budget), 89 MB retained, 19 correct patterns, exact population counts, ~41,600 URLs/s, byte-identical resume. Bounded min-heap-by-hash sampler landed here (ahead of schedule). Legacy pattern-extraction defect found and replaced with a prefix trie (ADR-0012) after corpus testing proved the legacy algorithm structurally wrong (min-observation floor of 3, one shared path-position counter). Three further tree-algorithm bugs caught only by the adversarial corpus (§1.10 in coding standards now). Sampling-hash uniqueness-constraint bug found and fixed (migration 0001) — sample_observation was uniquely constrained on url_hash, silently dropping real observations because the min-heap sampler concentrates retained hashes in the collision-dense low end of the hash space.
M3 (Phase 1 confidence math) — complete. Wilson score confidence intervals with finite-population correction, and adaptive sample expansion wired to the min-heap's expansion bounds. Validated against published Wilson values (not the package's own arithmetic) — this caught two wrong hand-computed reference expectations (a missed FPC shrink, a misquoted published value). Found and fixed: a float-epsilon defect at p̂ = 1 that would have violated audit_snapshot's CHECK constraint; confidence-band classification needed two threshold pairs, not one (ADR-0013), since width-relative-to-estimate and width-relative-to-population break in different regimes. Accepted trade-off: a mid-range-error large pattern is structurally capped at approximate confidence under a 400-probe first round, since the estimate is already decision-sufficient and further probes cost real requests for no gain.
Post-M3 hardening pass (PR #5) — complete, 2026-09-02. Nine Copilot Code Review findings across the M0–M3 stack, all confirmed real, fixed in one consolidated PR against develop. The significant one: the M1 cross-tenant FK gap above. The onboarding-breaking one: .env.example's AUTH_SECRET="" failing its own validation, breaking the README's documented first command. Also fixed: node-postgres returning sum(...)::bigint as a string, not a number; NULL-sort ordering; a PatternTrie.merge() memory-cap undercount; a finalize() claiming false idempotency; a silent no-op on bad CLI input; a discarded XML root tag; hits aggregated before validation. Separately found and fixed: the GitHub Actions workflow never triggered on push to develop, only main/pull_request — every earlier "CI green" claim had only been checked on a PR's source branch, never after merge. PRs #1–#5 merged bottom-up into develop (b5a5998).
First main promotion — complete, 2026-09-02 (PR #7, merge 5b6ff28). main had held nothing but the original scaffold until now; it carries M0–M3 plus the post-M3 hardening pass for the first time. Its own fresh pull_request CI run (16 steps, all green), job logs read directly to confirm constraints.test.ts (12), isolation.test.ts (8), and schema.test.ts (4) actually executed against real Postgres rather than being skipped — the local-develop-green result was not assumed to carry over automatically. main does not yet carry M4 or M5 — a second develop → main cycle is needed, timing is an open call (see Open decisions below).
M4 (Phase 2 opening — Impact Score) — complete, merged 79930e8. severityFor, the Impact Score's severity-weighting function, ships with no default table — a missing argument throws rather than shipping a guessed answer. The severity table itself (410/404-first ranking) was ratified by the project owner, not guessed, recorded as ADR-0014 with per-class reasoning. Two rules locked in by tests: a refusal (HTTP 403) can never carry impact, enforced at the database level (otherwise a crawler-blocking-but-healthy site would rank above genuinely broken ones); total volume can outweigh severity class in the final score (50,000 redirect chains outrank 200 gone pages) — deliberate, caught the implementer's own initial (backwards) assumption during test-writing, now pinned against silent inversion. Copilot Code Review did not run on this PR (its auto-run had stopped after PR #4, cause undiagnosed as of M5) — a manual review pass for the same defect classes found one real, merge-blocking issue: the GSC-traffic-factor hook, documented as arriving "as one multiplication," could push a computed impact_score past the value ck_audit_snapshot_impact_sane allows (a 2.5× multiplier on a 100,000-URL estimate → 250,000, insert rejected) — neither the hook nor the constraint showed this defect in isolation, only their interaction. Bounded to (0, 1] before merge: the multiplier can only de-weight an impact score, never amplify it. Also fixed: an empty sampling plan returning flag_for_review (routing a human to review a pattern with nothing in it) instead of recognizing there was nothing to review; two smaller doc/behavior mismatches. Fresh push-triggered CI run on develop confirmed green post-merge.
M5 (Phase 2 — HTTP verification client) — open as PR #8, CI green, not yet merged. 55 tests, entirely mocked at the transport boundary — deliberately, since a suite that actually probed real servers would reproduce the exact request behavior the rate limiter and circuit breaker exist to prevent. Delivered: HEAD-first, GET-only-on-suspicious verification; the M4 escalation-cap policy wired into a real client for the first time, charged against the planned sample size and correctly counting an escalated check as two requests (HEAD + GET sniff), not one — so 20% of a 30-URL plan is 30 HEADs plus 6 sniffs (36 total), not 60; rate limiting charged per actual request, not per logical "check" — fixing a real, measured legacy defect (the legacy engine metered per check and, because a 2xx result still costs a HEAD plus a body sniff, actually sustained ~49.17 req/s against a nominal 25 req/s ceiling). The caller (not packages/http itself) owns the request-profile ladder — a deliberate design choice that let host-strategy negotiation be cleanly deferred rather than half-built inside this milestone. Deliberately left undone, not silently cut: host-strategy negotiation. A host that would respond fine to a browser-profile request is currently just reported "blocked," with no way to distinguish "refuses every profile" from "refuses this one." The real fix needs a host-profile table, a rung ladder of profiles to try in order, and a Redis-backed hot copy for request-time lookups — scoped and costed as ADR-0016, treated as its own milestone rather than a corner of M5.
Open question from M1, still not resolved by M2–M5: the schema doesn't yet visibly carry forward the shape/stratum distinction (structureClusters/shapeStrata/pattern_shape_rules) the original review flagged as valuable. Needs a direct answer before the PopulationProfile open decision below gets marked resolved.
CI/PR infrastructure — resolved as of M3/post-M3, with a new coverage gap found at M4. The original PR/CI gap (open after M1 and M2) turned out to be a mis-scoped fine-grained PAT, not unpushed code — fixed, four PRs opened stacked bottom-up, CI verified green in GitHub's real environment including the M1 Postgres service container. A second gap (no push trigger on develop) was found and fixed in the post-M3 pass. main has now been promoted for the first time (PR #7). New gap found at M4: Copilot Code Review auto-ran on PRs #1–#4 but went silent on #5, #6, and #7, and an explicit reviewer request on a later PR didn't take either — cause not yet diagnosed. Issues and gaps in the review

Confidence intervals are named but not defined. Use the Wilson score interval, not a naive normal approximation. Implemented in M3.

No finite-population correction. Implemented in M3, including adaptive-expansion wiring.

Hash-threshold sampling and reservoir sampling are conflated. The bounded min-heap-by-hash approach gives both exact size and growability. Implemented in M2, ahead of schedule.

The repo-specific claims are unverified in this session. Confirmed via Phase 0 (M0) — see Implementation progress above.

No multi-tenant resource isolation. BullMQ queue/Redis/connection-pool isolation per site/tier — still pending as of M5. Database-level isolation (partitioning, compile-time query guard, schema-level FK pairing) landed early (M1, corrected post-M3).

PopulationProfile may duplicate what already exists. Still open as of M5 — see Open decisions below.

No cost or infrastructure budget analysis. Still open — see Open decisions below (platform-wide request budget).

No observability or audit-trail plan. Partially addressed in spirit by the "signal, don't silently succeed" pattern now standard across M2–M4 (empty sitemap, bad CLI input, false idempotency, empty sampling plan all treated as the same defect class), but no actual dashboards yet — still Phase-5-adjacent work.

The GET-fallback escalation isn't bounded. The policy was decided in M4 and wired into a real client in M5 — a budget against the planned sample size, correctly costing an escalated check as two requests, not one, and rate-limited per actual request (fixing a measured legacy defect: ~49.17 req/s against a nominal 25 req/s ceiling from per-check-not-per-request metering). The soft-404 GET body-size cap itself and host-strategy negotiation (ADR-0016) remain open — the latter explicitly scoped as its own milestone.

Open decisions
Is PopulationProfile new, or does it consolidate pattern_shape_rules / structureClusters / shapeStrata? Still open — not touched by M2 through M5.
What severity weights should the initial Impact Score use? Resolved, M4 — ADR-0014.
What's the acceptable platform-wide HTTP request budget per day/month, and do any of the 650 target sites have contractual/robots.txt constraints that should cap it further? Still open.
Does "multi-user" for the AWS deployment mean the internal Asapsemi team, or will external clients log in? Settle before Phase 3.
New at M5 — does host-strategy negotiation (ADR-0016) come immediately after M5, or wait behind pipeline-orchestration work? Framed by the M5 implementer as a genuine trade-off, not guessed at: building it next closes a real correctness gap (a site currently reported "blocked" may only be refusing one request profile) before more work is built on top of the HTTP client's current behavior; waiting means the orchestration work that actually runs sampling → verification → scoring end-to-end lands sooner, which is what would make the pipeline demonstrable at all. No default assumed — needs the project owner's call.
New at M4/M5 — is Copilot Code Review worth actively fixing, given it's gone silent since PR #4? It found 9 real issues out of 9 flagged in its one completed pass (the post-M3 hardening pass) and 0 issues on the PRs after, because it didn't run — not because those diffs were clean. Given that hit rate, the recommendation leans toward diagnosing and re-enabling it rather than accepting manual review alone as the permanent substitute, but this is a workflow-tooling call for the project owner, not a unilateral one.
