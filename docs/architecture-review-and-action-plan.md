Pattern-Aware SEO Platform — Architecture Review & Action Plan

Source: architecture review conducted in a shared ChatGPT conversation (against the feature/aws-s3-sftp-deploy branch and an uploaded code ZIP), critiqued and turned into an action plan on 2026-09-01. Tech stack recommendation added the same day. Implementation progress (M0, M1, M2) logged 2026-09-01; M3, initial CI verification, a post-M3 hardening pass, the first main promotion, M4 (with a merge-time correction), M5, the bundled M4+M5 main promotion, and M6 (full pipeline orchestration) all logged 2026-09-02.

Context

The review examined the existing sitemap migration/health-check engine (Next.js frontend, Fastify backend, BullMQ + Redis, PostgreSQL, streaming SAX sitemap parsing, Piscina for CPU-heavy work, S3/SFTP deployment) and concluded the direction is sound: don't rewrite it, evolve it into a pattern-aware, sampling-based SEO intelligence platform that can audit sites with tens or hundreds of millions of URLs without crawling the whole URL universe. The core idea — collapse 90M+ URLs into a few thousand patterns, sample each pattern, verify statistically, and only do targeted deep audits where evidence says to — is the real differentiator and is worth keeping as the north star.

Deployment path: local development on the team's own Mac/Windows PCs first, then deployment to AWS for multi-user access, with model training on the accumulated sampling data planned as a later phase.

Implementation progress
M0 (Phase 0 foundation) — complete. Tooling/enforcement, real workspace packages, packages/shared, initial apps/web scaffold, docs/decisions.md established.
M1 (Phase 1 schema/tenancy) — complete; one correction found post-M3. Core entity model (organization → site → sitemap_run → sitemap_file → pattern → pattern_population / pattern_sample → sample_observation, plus audit_snapshot/sampling_health), degenerate-interval CHECK constraint, compile-time tenant isolation, composite (site_id, id) PKs (ADR-0010). Correction (post-M3, migration 0002): the compile-time query guard was real, but the schema itself allowed a cross-tenant reference — a row could carry one site's site_id while a FK pointed at a different site's parent row, because only the FK column was constrained, not the (site_id, id) pair on the referenced side. Closed via UNIQUE (site_id, id) plus five repointed FKs; isolation.test.ts gained explicit cross-site cases. Two isolation layers — query-time and schema-time — each need their own proof.
M2 (Phase 1 streaming ingestion + pattern extraction) — complete. Single pass over a synthetic 10,000,000-URL corpus: 681 MB peak RSS (1,536 MB budget), 89 MB retained, 19 correct patterns, exact population counts, ~41,600 URLs/s, byte-identical resume. Bounded min-heap-by-hash sampler landed here (ahead of schedule). Legacy pattern-extraction defect found and replaced with a prefix trie (ADR-0012) after corpus testing proved the legacy algorithm structurally wrong (min-observation floor of 3, one shared path-position counter). Three further tree-algorithm bugs caught only by the adversarial corpus (docs/CODING_STANDARDS.md §1.10). Sampling-hash uniqueness-constraint bug found and fixed (migration 0001) — sample_observation was uniquely constrained on url_hash, silently dropping real observations because the min-heap sampler concentrates retained hashes in the collision-dense low end of the hash space.
M3 (Phase 1 confidence math) — complete. Wilson score confidence intervals with finite-population correction, and adaptive sample expansion wired to the min-heap's expansion bounds. Validated against published Wilson values (not the package's own arithmetic) — this caught two wrong hand-computed reference expectations (a missed FPC shrink, a misquoted published value). Found and fixed: a float-epsilon defect at p̂ = 1 that would have violated audit_snapshot's CHECK constraint; confidence-band classification needed two threshold pairs, not one (ADR-0013), since width-relative-to-estimate and width-relative-to-population break in different regimes. Accepted trade-off: a mid-range-error large pattern is structurally capped at approximate confidence under a 400-probe first round, since the estimate is already decision-sufficient and further probes cost real requests for no gain. Tuning observation, not yet acted on (M6): firstRoundSampleSize draws 30 of a 40-URL population — a small pattern stays statistically estimated when 10 more requests would make it a full census instead, which would be both simpler and more informative for roughly the same request cost. Worth folding into a future revisit of the first-round sizing heuristic: when the remaining gap to full population is small relative to the planned sample, prefer a census.

Widening packages/database's single-entry-point export to share its test harness was also correctly left undecided rather than done unilaterally — resolved here: add a narrow packages/database/testing export subpath for test-only use (a migrated-pool factory), guarded by its own compile-guard test asserting it's never imported outside test files, with the main . entry point unchanged; needs its own ADR at implementation time (docs/CODING_STANDARDS.md §1.4). Issues and gaps in the review

Confidence intervals are named but not defined. Use the Wilson score interval, not a naive normal approximation. Implemented in M3.

No finite-population correction. Implemented in M3, including adaptive-expansion wiring.

Hash-threshold sampling and reservoir sampling are conflated. The bounded min-heap-by-hash approach gives both exact size and growability. Implemented in M2, ahead of schedule.

The repo-specific claims are unverified in this session. Confirmed via Phase 0 (M0) — see Implementation progress above.

No multi-tenant resource isolation. BullMQ queue/Redis isolation per site/tier implemented in M6 (per-site, per-tier queue keys, {tier}:{siteId}:{stage}). Connection-pool budgeting per worker type still pending. Database-level isolation (partitioning, compile-time query guard, schema-level FK pairing) landed early (M1, corrected post-M3).

PopulationProfile may duplicate what already exists. Still open as of M6 — see Open decisions below.

No cost or infrastructure budget analysis. Still open — see Open decisions below (platform-wide request budget).

No observability or audit-trail plan. Partially addressed in spirit by the "signal, don't silently succeed" pattern now standard across M2–M6 (empty sitemap, bad CLI input, false idempotency, empty sampling plan, and — new at M6 — the never-before-exercised impact_score write and the additive-write durability gap all treated as the same defect class), but no actual dashboards yet — still Phase-5-adjacent work.

The GET-fallback escalation isn't bounded. The policy was decided in M4 and wired into a real client in M5; M6 found and fixed an inverted comparison in that same cap once it was wired into the real pipeline (see Implementation progress, and docs/CODING_STANDARDS.md §1.13 on why this specific failure shape — correct in isolation, wrong composed — keeps recurring). The soft-404 GET body-size cap itself and host-strategy negotiation (ADR-0016) remain open.

Phase 5 — SEO evidence and audit layer (later)

Started as of M7 (2026-09-03), earlier than this phase's ordering implies, and deliberately: with the pipeline landed there was real measured data and nothing that could read it, so the platform was not demonstrable. Three screens exist — a sites list, a site detail, and the pattern evidence page — as Server Components over a Fastify API, with the ADR-0008 rendering contract enforced by a component whose type makes an interval-less estimate unconstructable, plus the CI guard that ADR asked for. Still not built, and scoped to D3 rather than dropped: the slide-over drill-down (docs/DESIGN.md §6), the Cmd+K command palette named as the primary navigation surface, j/k keyboard navigation, the density toggle, sparklines, and the three Magic UI motion moments (§8). Auth is deferred: the API acts as one organization under a system scope (ADR-0026), and every route already takes a scope as a parameter, so session auth replaces one function without changing a call site.

Known gap, carried forward from M6 and restored here after an M7 doc pass found it had been dropped in that milestone's rewrite: stratification is not yet wired into the draw. The estimate stage computes over a single stratum — which is exactly the Wilson-plus-FPC interval, and is honest about being that — but the stratified path estimateStratified already supports has no producer. Until it does, a pattern whose error rate varies sharply by {param} value is estimated as if it were homogeneous: the interval stays honest about its width without ever being narrow enough to act on. This is precisely the case structureClusters and the one-slot stratification choice exist to serve, and it connects to the shape/stratum open question at the top of this document.

M7 (API + evidence screens) — complete, 2026-09-03. 356 tests. The first milestone begun by a different session and finished by review rather than written from scratch: ~1,900 lines of API, screens and a demo seed arrived uncommitted, were committed verbatim as a checkpoint so their diff stayed separable, and were then repaired. Kept, because it was genuinely good: the <Estimate> component enforces ADR-0008 through a discriminated union on evidence tier, so an interval-less estimated value is unconstructable rather than merely discouraged; docs/DESIGN.md compliance is structural (the Tailwind colour and radius namespaces are reset to nothing, so rounded-2xl and bg-indigo-500 do not compile); and the seed script runs the real estimator over synthetic observations rather than typing plausible numbers in, writing no audit_snapshot at all for blocked and needs_review because there is no honest claim to publish.

Seven defects, found by probing the running system rather than by reading it. The one that mattered: routes/patterns.ts built a SiteScope with siteScopeWithin and never called findSiteById, so both pattern routes read run, pattern, sample and observation rows keyed on a caller-supplied siteId with no organization linkage — every repository beneath filters on site_id alone, correctly, because a SiteScope is supposed to have been vouched for already, and siteScopeWithin's own doc says the caller owes that check. Latent only because one organization exists. A regression test seeds a second tenant with real rows and asserts the leak, confirmed load-bearing by removing the guard and watching another organization's pattern and its published claim come back. Next: no runtime validation existed anywhere, so a non-UUID path segment reached a Postgres uuid comparison and Fastify serialized the driver error — raw query text and column list — as a 500; now zod through a type provider (ADR-0025), 400 before any query runs, and one error envelope that never carries internals. Also: authenticatedOrganizationScope was stamping origin: "request" with no session in existence, so every audit line attributed a hardcoded identity to a user (now systemOrganizationScope, ADR-0026); OrganizationNotSeededError was documented as surfacing "per-request as a clear 503" while nothing registered an error handler, so it produced a generic 500 — §1.9's own failure shape, a comment asserting a guarantee the code does not make; a site with no finished run returned 404, making a freshly-onboarded site indistinguishable from a typo in the URL; and impact_score rendered as a bare toFixed(1) with no ~ and no interval, identically whether the tier was counted or estimated, despite being point_estimate × severity_weight and therefore exactly as estimated as the count it weights (ADR-0024 derives the bounds from severity_weight and confidence_level, both of which were being written to audit_snapshot and never selected — no migration needed).

Zero tests existed for any of it, and "vitest run --passWithNoTests" kept CI green over that: a suite passing by vacuum, which is the shape this project has treated as worse than a red one since M0. 35 tests now cover the API and the screens. Two found real defects rather than confirming behaviour: patternStatusTone mapped blocked to critical while severityTone mapped the same concept to unknown — schema/enums.ts warns about that inversion by name, because a host refusing us is not a site defect and reporting it as one lets a WAF turn a healthy client into a P0 — and the confidence band reached the reader through hue alone, so "low" was invisible in a screenshot and to anyone who cannot distinguish the tokens. ADR-0008's own enforcement clause ("a CI test asserts no page formats a sampled figure outside it") had never been implemented; it now exists as a scan that fails naming the file, the line and the remedy, verified by reintroducing the exact violation it was written for.

Composition again, for the third time in three milestones (§1.13): buildApp took the whole validated Config, so constructing it in a test validated every variable the platform has — including REDIS_URL, which no route touches. Narrowed to the two keys it actually reads, with the real Config still satisfying it structurally at the call site. This is the same defect as M6's runIngest calling getConfig(), and it recurred in a different package within a day of being written down.

packages/database/testing landed as CODING_STANDARDS §1.4 recorded it on 2026-09-02, with both attached conditions enforced by tests rather than review (ADR-0023): the exports-map guard asserts the exact sanctioned set, and a second guard asserts the subpath is imported only from test files and never from apps/*/src — which is why apps/api's tests live in apps/api/test/ rather than beside the source. The first version of that guard flagged a docblock that merely described the rule, so it now matches import syntax rather than any mention; a grep-shaped guard has to be verified both ways, on a planted violation and on a file that only talks about the thing. packages/pipeline's duplicated harness is deleted, along with the pg devDependency it needed.

Four smaller things worth not rediscovering. pnpm seed:demo and db:migrate never loaded .env — the apps use --env-file-if-exists and the scripts did not — so the seed script instructed you to create a .env file it then ignored. The demo run was stamped isDryRun: false, status complete, patterns measured, which made manufactured evidence indistinguishable at the data layer from a measured audit; the org slug and worker id were the only tells and nothing queries either, so it is isDryRun: true now. WEB_API_URL was read with a hardcoded fallback and declared in neither config, .env.example nor turbo.json — exactly the shape §4 was amended to warn about, where Turborepo filters an undeclared variable out and setting it appears to do nothing. And the legacy Sitemap_Migration backend holds port 3001 on the developer's machine (its frontend holds 3000), which is the same class of collision as the native Postgres on 5432 that bit M1 — overridable ports, not a stopped service.

Auth is deliberately deferred rather than half-built, and docs/DESIGN.md's larger surfaces with it: the slide-over drill-down, the Cmd+K palette named as the primary navigation surface, j/k navigation, the density toggle, sparklines and the three Magic UI motion moments are all scoped to D3 and named there rather than quietly dropped. ADRs 0023–0026 recorded. docs/DESIGN.md also moved from the repo root into docs/ to match where CLAUDE.md and six other references had always said it was, with two genuinely broken README links fixed in passing.

Cross-cutting: observability (start in Phase 1, not later)
Dashboards for sampling convergence rate, confidence-band distribution, GET-escalation rate, per-site request volume against budget — not yet built.
A way to reconstruct exactly which inputs produced a given historical report — not yet built.
"A run that completes without throwing may still be a silent failure" is now a recurring, named defect class (empty sitemap parse, bad CLI input, false idempotency, empty sampling plan, an unexercised write path, an additive-write durability gap) — worth a dashboard signal of its own once observability work starts, not just per-instance fixes.
CI observability needs to cover which branch a workflow actually triggers on and which env vars a monorepo task actually receives (the M6 Turborepo finding), not just whether a given run is green.
Automated-review coverage (Copilot or equivalent) needs to be monitored too — it silently stopped running on PRs after #4, and that would have gone unnoticed indefinitely without an explicit check; still unresolved as of M6.
New at M6: composition-shaped defects (docs/CODING_STANDARDS.md §1.13) are now the single most common real-bug category in this codebase (five confirmed instances across M2/M5/M6) — an end-to-end test against real dependencies is what's actually been catching these, not any per-package suite; worth treating "does the assembled pipeline produce a row that satisfies every constraint, on real dependencies" as a standing, required check for every future milestone that adds a new stage or wiring point, not an occasional exercise.
Open decisions
Is PopulationProfile new, or does it consolidate pattern_shape_rules / structureClusters / shapeStrata? Still open — not touched by M2 through M6.
What severity weights should the initial Impact Score use? Resolved, M4 — ADR-0014.
What's the acceptable platform-wide HTTP request budget per day/month, and do any of the 650 target sites have contractual/robots.txt constraints that should cap it further? Still open.
Does "multi-user" for the AWS deployment mean the internal Asapsemi team, or will external clients log in? Settle before Phase 3.
Does host-strategy negotiation (ADR-0016) come immediately after M6, or wait behind further pipeline work? Framed by the M5 implementer as a genuine trade-off, not guessed at — still unresolved as of M6, and now competing directly against the fleet-wide auto-attach decision below for priority. No default assumed — needs the project owner's call.
Is Copilot Code Review worth actively fixing, given it's been silent since PR #4? It found 9 real issues out of 9 flagged in its one completed pass and 0 on every PR since, because it didn't run — not because those diffs were clean. Given that hit rate, the recommendation leans toward diagnosing and re-enabling it rather than accepting manual review alone as the permanent substitute (manual passes have in fact been catching real, sometimes serious issues since — M6's additive-write durability gap among them — so the substitute is working, but a second independent check finding 9/9 on its only real run is worth having back). This is a workflow-tooling call for the project owner, not a unilateral one.
New at M6 — should the worker be granted a cross-organization read for fleet-wide auto-attach? Every packages/database read is scoped to one tenant by construction (§1.4/compile-time isolation); auto-attach (a worker automatically picking up newly-added sites across organizations) needs a read that crosses that boundary deliberately. This is a real decision about where the tenant-isolation boundary's one sanctioned exception lives, not a wiring detail — correctly not decided unilaterally during M6. Needs the project owner's call on scope (a dedicated, narrowly-typed cross-tenant read path, logged/audited separately from normal tenant-scoped access, is the shape I'd recommend when this gets picked up — but the decision to grant it at all is the project owner's, not mine to make by default).
Should packages/database's single export be widened to share its test harness? Resolved, M6 — see Implementation progress and docs/CODING_STANDARDS.md §1.4. A narrow packages/database/testing subpath, test-only, with its own compile guard; needs an ADR at implementation time.

Notes on the table (adjustments to the original proposal)
Frontend on AWS — the original proposal also lists Amplify Hosting or EKS or Vercel-then-AWS as options. ECS Fargate is the one to plan around here, since API and workers are already going to ECS — keeping the frontend on the same platform avoids running a second deployment system for no real benefit at this stage.
Redis locally — the original proposal says "Redis via Docker or local Redis." On Windows there's no supported native Redis build, so Docker is not optional there; only macOS can realistically run it natively (via Homebrew). Use Docker Compose for both platforms so Mac and Windows environments stay identical.
Database on AWS — the original proposal suggests Aurora Serverless v2 "if traffic is spiky." This workload's traffic (bursty population scans and sampling jobs) is spiky in exactly the way that makes ACU-based billing unpredictable before there's usage history to size it against. Start with a provisioned RDS instance sized from real local/staging load, add a read replica once dashboard read load justifies it, and revisit Aurora once there's billing data to compare. Partition the large per-URL and per-pattern tables by site_id from the start — cheap now, expensive to retrofit after 650 sites have data in an unpartitioned table.
ORM/query layer — Prisma and Drizzle are not interchangeable here. The sampling engine needs hash-based filtering, window functions, and CTEs close to raw SQL (Phase 1 above is largely about getting away from ORM-shaped queries like ORDER BY random()), and Prisma's query engine gets awkward exactly in that territory. Use Drizzle (or Kysely, a thinner type-safe SQL builder with no migration opinions of its own) for the packages/sampling, packages/sitemap, packages/http, and packages/pipeline query paths; Prisma is still fine for simpler CRUD — dashboard/admin, user and site management — if the team prefers it there. No need to standardize on one ORM for the whole codebase.
Local S3 testing — the original proposal suggests LocalStack for local S3 simulation. Since S3/SFTP deploy correctness is an active feature (feature/aws-s3-sftp-deploy), testing against LocalStack's emulation risks masking real-service behavior differences (auth edge cases, multipart upload thresholds, eventual consistency quirks) that only show up against actual S3. A dedicated low-traffic dev bucket costs close to nothing at this scale and removes that risk.
Auth — this depends on an open question (also listed above): does "multiuser" mean the internal Asapsemi team (RBAC across roles: admin/analyst/viewer), or will external clients ever log in? If internal, Auth.js (free, self-hosted, full control of the RBAC/org model) is the better fit than Clerk, whose per-user pricing and managed-org model are built for customer-facing SaaS. If external client logins are actually on the roadmap, Clerk's managed org support earns its cost. Settle this before Phase 3 (multi-tenant hardening) rather than defaulting to whichever library is easiest to wire up first.
Observability — the full OpenTelemetry + Prometheus + Grafana stack is right for the AWS multi-user phase, but standing it up for solo local development is overhead without payoff. For the PC-first phase, structured JSON logging plus the sampling-health tables already called for above (convergence rate, confidence distribution, escalation rate) is enough to build against. Add the full stack when deploying to AWS for multiple users, not before.
ML training — the original proposal only says to avoid Python for the main workers (correct — Node stays right for the streaming/sampling core), but doesn't address the model-training work that's actually planned (Phase 4 above). The right shape is a hybrid: keep the whole platform in Node/TypeScript as proposed, and add one small, separate Python service — a FastAPI app, or even just scheduled training scripts — that reads features from the same PostgreSQL database (the historical sample-outcome data Phase 4 starts collecting immediately) and either writes predictions back to Postgres on a schedule or serves a small internal /predict endpoint the Fastify backend calls when computing per-pattern sampling budgets. scikit-learn/XGBoost/LightGBM are the natural choices, matching Phase 4. This keeps the core platform's language unchanged while giving the ML work proper tooling — training in Node, or rewriting the platform in Python for the model's sake, are both the wrong trade.
Local development setup (Mac + Windows)

Use Docker Compose so Mac and Windows developers get identical environments:

yaml
# docker-compose.yml (simplified)
services:
  postgres:
    image: postgres:16
    ports: [\"5432:5432\"]
    environment:
      POSTGRES_PASSWORD: password
  redis:
    image: redis:7-alpine
    ports: [\"6379:6379\"]
  # Use a real low-traffic S3 dev bucket instead of LocalStack (note 5 above)

Run Next.js, Fastify, and the workers directly on the host (Node 22 LTS). Use concurrently or a simple package.json script to start the API, workers, and frontend together. Piscina works natively on both Apple Silicon and Windows. For large sitemap testing, mount a local folder or point at the real S3 dev bucket. This gets to zero-friction local development on day one.

Note (found during M0 on a Windows dev machine): a natively-installed Postgres can hold the default 5432 port and shadow the Docker container, causing connections to silently reach the wrong server. Make the compose file's host ports overridable (POSTGRES_PORT/REDIS_PORT env vars, defaults unchanged) so a machine with a port conflict can set a local override (e.g. 5433) in its own .env without changing the shared defaults.

Note (found post-M3): .env.example must itself pass the app's own env validation — it previously shipped AUTH_SECRET=\"\", which fails a min(1) zod check and broke cp .env.example .env && pnpm dev (the README's documented first step) immediately. Treat the example file as something that needs to actually work, not just document shape.

AWS deployment architecture

Start simple and scale later.

Phase 1 — MVP / early production:

Frontend, API, and workers: ECS Fargate (separate task definitions for the API and worker services; see note 1 on keeping the frontend here too rather than Amplify).
Database: Amazon RDS PostgreSQL, provisioned (not Aurora Serverless v2 — see note 3).
Redis: Amazon ElastiCache.
Storage: S3.
Load balancer: Application Load Balancer.
Secrets: AWS Secrets Manager.
CI/CD: GitHub Actions → ECR → ECS.

Later, once there's an actual scaling problem (100+ sites or heavy load):

Stay on ECS + Auto Scaling Groups if it keeps meeting needs — it's simpler and cheaper than Kubernetes for most teams; only move to EKS if finer control over worker-pool autoscaling becomes a real requirement, not a hypothetical one.
AWS Batch or Spot instances for very large one-off population scans.
SQS in front of specific job types only if a concrete durability gap in BullMQ shows up in practice — don't add it pre-emptively.
Why this stack fits

This matches the current direction — Next.js, Fastify, BullMQ, Redis, PostgreSQL, Piscina, and SAX streaming are already in place, so this is hardening, not a rewrite. It's local-first: everything runs on Mac and Windows with Docker Compose, no cloud required for development. Every component has a first-class managed AWS service, so the path to production doesn't require re-architecting. Fastify + BullMQ + Piscina + streaming SAX is a genuinely high-throughput combination for this specific workload — M2's benchmark (10M URLs, 681 MB peak RSS, ~41,600 URLs/s) is early evidence this combination performs as expected at the scale the product actually needs, and M6's full end-to-end pipeline run against real dependencies is the next level of that evidence. It's multi-tenancy ready — PostgreSQL (partitioned by site_id, with row-level security or schema-per-tenant as a later option) plus BullMQ queue isolation and Redis key namespacing (both landed as of M6) covers the 650-site end state. And it's cost-controlled: ECS Fargate + provisioned RDS starts cheap, and only the worker fleet needs to scale as load grows.

What to avoid

NestJS is too heavy and opinionated for this shape of workload. Don't put the main workers on serverless (Lambda) — long-running sitemap processing and Piscina worker pools are a bad fit for Lambda's execution model. MongoDB isn't the right choice here — the workload leans on relational and statistical queries (window functions, CTEs) that Postgres is built for. Don't replace BullMQ — it remains the strongest Node queue for this. And don't treat "avoid Python" as blocking the ML roadmap — the fix is a separate small Python service (note 8), not avoiding Python everywhere or rewriting the platform in it.

Frontend design tooling (in the coding assistant, not the product itself)

This is about what to plug into whatever coding assistant builds the Next.js frontend (Claude Code or similar) — not something the shipped product depends on. These tools solve two different problems — design taste (does the output look considered rather than generic) versus components (what gets installed into the codebase) — and it's worth keeping the two separate rather than picking one tool to do both.

Taste layer — pick one, don't run two at once, and Impeccable is the better fit here:

Impeccable (pbakaus/impeccable, open source) is the stronger choice for this specific project. Unlike a single automatic skill, it's a full design-vocabulary framework: one /impeccable skill with roughly 23 commands (init, shape, critique, polish, audit, typeset, colorize, animate, and more), backed by around 60 deterministic anti-pattern detectors (overused fonts, purple gradients, bounce easing, cards-in-cards, low-contrast gray text) and documented design decisions (PRODUCT.md/DESIGN.md) that keep a large surface area — a dashboard spanning 650 sites' worth of pattern health, confidence intervals, and impact scores — visually consistent as different people or sessions build different screens. Critically, its setup explicitly distinguishes "brand surfaces" (marketing/landing pages) from "product surfaces" (dashboards/tools/apps) and calibrates its checks accordingly — which is exactly the gap in Anthropic's own skill (next item). Install via npx impeccable install (auto-detects the Claude Code folder) or the plugin marketplace.
frontend-design (Anthropic's official Claude Code plugin) is a lighter, single automatic skill aimed at the same problem — steering away from generic "AI slop" (Inter font, purple gradients, rounded-corner three-box grids). It's worth knowing about, but it leans maximalist/bold by default with no equivalent "this is a dashboard, not a landing page" mode, so it needs to be explicitly and repeatedly steered toward a clean, information-dense enterprise style for this project. Given Impeccable already handles that distinction natively, install Impeccable instead of this one for the dashboard — there's little reason to run both, since two taste-layer skills active at once can give the coding assistant conflicting instructions.

Component layer — shadcn/ui MCP, not Magic UI, for this project:

shadcn/ui MCP (official, from ui.shadcn.com) is the one to install, because shadcn/ui is already the chosen component library in the stack above. It lets the coding assistant browse, search, and install real shadcn components and blocks — including shadcn's own dashboard blocks — directly into the codebase via natural language, and supports a private company registry later if a shared internal design system gets built. Install with pnpm dlx shadcn@latest mcp init --client claude, or configure manually via .mcp.json.
Magic UI MCP (magicuidesign/mcp, from magicui.design) adds animated marketing-style components — marquees, particle/grid backgrounds, animated beams — on top of shadcn/ui and Tailwind. Good for a public-facing landing or marketing page for the product, but a poor fit for this dashboard: those effects fight readability in a dense interface built around tables, health scores, and status badges. Superseded by docs/DESIGN.md, which names three specific, narrow uses for Magic UI in the actual product surface — see that document, which is more specific than this note and wins.
Note the name collision: "21st.dev Magic MCP" (21st-dev/magic-mcp) is a different, unrelated project — an AI-driven UI generator pulling from 10,000+ components across many different design systems, closer to a v0-style generator than a scoped component installer. Mixing it in alongside shadcn MCP risks visual inconsistency, since it isn't scoped to one design system. Not recommended here.
Third-party AI wireframe/design generators (e.g. Google Stitch): structural/IA reference only, never a visual source of truth — see docs/DESIGN.md §11 for the full guardrail, added after a real Stitch export for this product was evaluated and found to default straight into the banned indigo/violet accent and the banned boxed-KPI-card dashboard layout.

Recommended combination for this project: Impeccable (taste layer, set up as a "product surface"/dashboard from its init step, pointed at docs/DESIGN.md) + shadcn/ui MCP (components, including its dashboard blocks) + Tremor/Recharts for charts (already in the stack above). Skip frontend-design and 21st.dev Magic MCP for the core dashboard; Magic UI is used narrowly per docs/DESIGN.md §8, not generally. This section became load-bearing at M7: the first three screens are built to docs/DESIGN.md's token layer, hand-rolled rather than assembled from shadcn/ui blocks. Neither Impeccable nor the shadcn/ui MCP has been used yet, so the drift-checking this section recommends is still unexercised — worth doing before D3 adds the denser surfaces, not after.

Final recommendation

Stick with and harden the current direction: Next.js 15/16 + Fastify 5 + BullMQ + Redis + PostgreSQL 16 + Piscina + TypeScript for the platform, plus one small separate Python service for model training and inference once Phase 4 has enough historical data to train on. For the coding assistant building the frontend, pair Impeccable (design taste, set up for a product/dashboard surface) with the shadcn/ui MCP (components). This is the strongest combination for a pattern-aware, sampling-based SEO platform that needs to run locally today, look genuinely professional rather than templated, and scale to AWS with multiple users and, later, ML-driven sampling.
