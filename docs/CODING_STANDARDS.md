Coding Standards — Pattern-Aware SEO Platform

This document exists so code in this repo looks like it came from one team with one set of habits, whether it was written by a person or an AI coding agent, on Monday or six months from now. It draws on established, publicly documented style guides rather than inventing rules from scratch — see References at the end for the source material. Where this document and a referenced guide disagree, this document wins for this repo; the references are there for the reasoning, not to be followed blindly over project-specific needs (this project's sampling/statistics code, for instance, has correctness requirements no general style guide addresses).

Enforcement: these rules are meant to be checked by tooling (ESLint, Prettier or Biome, tsc --strict, a SQL linter) wherever a rule can be mechanically checked, not left to memory or code review alone. Section 4 lists the specific tooling.

1. TypeScript & Node.js
1.1 Compiler settings

strict: true in every tsconfig.json, no exceptions. That means noImplicitAny, strictNullChecks, strictFunctionTypes, and the rest of the strict family are all on. Target ES2022, module NodeNext (matches Node 22's native ESM support). skipLibCheck: true is fine for build speed; noUncheckedIndexedAccess: true is recommended for packages/sampling and packages/sitemap specifically, since off-by-one and undefined-access bugs in those packages are exactly the kind of thing that silently corrupts a sampling result rather than crashing loudly.

1.2 Naming
Element	Convention	Example
Variables, functions, methods	camelCase	computeConfidenceInterval
Classes, interfaces, types, enums	PascalCase	PatternSample, SamplingStrategy
Type parameters	single uppercase letter or short PascalCase	T, TResult
Constants (true, compile-time constants)	UPPER_SNAKE_CASE	MAX_SAMPLE_SIZE
File names	kebab-case.ts	confidence-interval.ts, pattern-population-pool.ts
Enum members	PascalCase	SampleMethod.MinHeapByHash
Boolean variables/props	prefixed is/has/should	isConverged, hasEscalated

Consistent file naming matters more than which convention is picked — kebab-case.ts is the choice here because it's case-insensitive-filesystem-safe (avoids Mac/Windows vs. Linux mismatches that PascalCase filenames can cause) and matches most of the modern Node ecosystem.

1.3 Exports and modules

Named exports only — no export default. Default exports make renames and re-exports harder to track mechanically and are explicitly discouraged by the Google TypeScript Style Guide for the same reason. ESM only ("type": "module" in every package.json); no require() in new code. Use import type { X } from "..." for type-only imports so they're erased cleanly at build time. Import order: Node built-ins, then external packages, then internal workspace packages, then relative imports — each group separated by a blank line and (where tooling allows) alphabetized within the group.

1.4 Types

Prefer interface for object shapes that describe data (especially anything mirroring a database row or an API payload) and type for unions, intersections, and utility-type compositions. Never use any; if the type genuinely isn't known yet, use unknown and narrow it before use. Avoid the non-null assertion operator (!) except with an inline comment explaining why the value is guaranteed non-null — an unguarded ! on sampling data is exactly the kind of thing that turns a missing sample into a runtime crash three layers away from the actual bug.

A package's public surface can enforce structural rules the type checker doesn't give you for free — e.g. exposing an opaque type with no query methods, and a single entry point, so a whole class of bug (an unscoped/cross-tenant query) becomes a compile error outside that package rather than a runtime risk to catch in review. packages/database does this for tenant-scoped queries (see ADR references in docs/decisions.md). Prefer this "make the wrong thing impossible to write" approach over a lint rule or a code-review checklist item whenever the type system can actually express the constraint.

Widening a locked-down export surface is an architectural decision, not an implementation detail — treat it accordingly. packages/database publishes exactly one entry point (.) by design, verified by compile-guards.test.ts. When a consumer needs something the single entry point doesn't offer (M6: packages/pipeline needed a migrated Postgres instance for its own tests), the right move is to raise the question, not to widen the export map unilaterally or route around it with a duplicated ad hoc harness by default. Decision recorded here (2026-09-02): add a second, narrow export subpath — packages/database/testing — that exposes a migrated-pool/test-harness factory for use only from test files. This does not loosen ., which stays exactly as restrictive as it is today; it gives test code a legitimate, shared way to get a real migrated database without every package reinventing migration-running boilerplate. Two conditions make this safe: (1) /testing must never be imported from apps/*/src or any non-test file — add a compile-guard test for this alongside the existing one for ., the same discipline that protects the main entry point; (2) this needs its own ADR when implemented, since it changes the package's public contract. Record the ADR number in docs/decisions.md at implementation time.

1.5 Async code and error handling

Always async/await — no raw .then() chains, no callback-style APIs in new code. No floating promises: every promise is either awaited, returned, or explicitly voided with a comment explaining why it's fire-and-forget. Biome cannot express the type-aware promise rules (no-floating-promises, no-misused-promises) — run a narrow, type-aware ESLint pass for exactly those two rules alongside Biome for everything else (see §1.11 and ADR entries in docs/decisions.md); this is not "running two linters," it's Biome plus the one category of check it structurally can't do. Throw Error subclasses, never strings or plain objects — define a small hierarchy of domain errors (e.g. SamplingError, PopulationScanError) rather than throwing generic Error everywhere, so callers can distinguish expected failure modes from bugs; an explicit flag distinguishing an expected failure (a host refused a request) from a defect (the code is broken) is worth adding to the base error type, not just a message string. Never swallow an error silently (an empty catch {} block is a defect, not a shortcut) — at minimum log it with enough context to reproduce.

A technically-successful run can still be a silent failure. "The job completed without throwing" and "the job did what it was supposed to" are not the same claim, and code should not conflate them. Concrete instances found in this codebase: a streaming XML parser processing a whole chunk synchronously meant an oversize-file guard never actually fired (M2); an HTML error page is well-formed enough XML that it parses successfully and yields zero URLs, indistinguishable downstream from a site that legitimately lists nothing (M2); an empty sampling plan silently routed to flag_for_review — a human sent to review a pattern with nothing in it — rather than recognizing there was nothing to review in the first place (M4). Whenever a run can complete "successfully" with a semantically empty or suspicious result, surface that explicitly — a warn-level log at minimum, a dedicated status on the resulting row where one exists (e.g. audit_snapshot/sampling_health) — rather than letting it look identical to an ordinary success. Don't rely on "it didn't throw" as evidence that it worked.

The silent-failure rule reaches the presentation layer, and exposing a table for the first time is when it gets tested. The rule above is usually read as being about pipelines, but the indistinguishability it forbids is re-created by whatever finally renders the row. D3a's run-detail screen surfaced sitemap_file for the first time and showed a file with parse_status = 'parsed' and url_count = 0 in healthy green, visually identical to a file holding 5,700 URLs — the exact M2 case from the paragraph above, restored by a status enum that cannot express it, because the parse genuinely did succeed. A status column is not always sufficient to classify health: where the distinction depends on a second value, the classifier takes both (sitemapFileTone(status, urlCount)) and the row states the qualifier in words rather than leaving it to a colour. When a screen renders a column nothing has rendered before, check what its most benign-looking value would mean, and expect to find a case the status alone gets wrong.

A capped read must disclose its cap, and a figure derived from a capped page must not be labelled as a total. Same family: an answer that looks complete and is not. D3a found both fleet screens fetching the API's default page of 50 rows and computing their KPI cards from rows.length — so "findings: 50" meant "at least 50", and every derived count was a lower bound presented as exact. Two obligations follow. First, a route that caps a list sends the real count alongside it (countSitemapFiles beside a 200-file page), counted rather than read from a progress counter written by some other stage — the two disagreeing is itself worth surfacing. Second, a caller that requests a page passes its limit explicitly rather than inheriting a default it does not know the value of, and any figure it derives from a full page is marked as a bound. This is DESIGN.md section 9's ban on manufactured precision arrived at from the pagination side rather than the statistics side, and it applies to a counted figure — a page boundary makes an exact count into a lower bound without any sampling being involved.

Destroying a response body after a probe already resolved can still raise. A real socket's lifecycle doesn't end when your code stops reading it — an HTTP client tearing down a response body it's done with can still emit an async error event afterward (M6: probe.ts destroying undici bodies raised uncaught AbortErrors that arrived after the probe had already returned success). Code that reads, discards, or aborts a body/stream after using it needs an explicit handler for errors arriving on that teardown path, not just on the read path — and this is exactly the class of bug that mocked-body tests cannot catch (see §1.10).

1.6 Logging

Structured logging via pino (Fastify's default, and reused as-is in the worker) — no console.log in application code paths; it's fine in one-off scripts under scripts/ but not in apps/*/src or packages/*/src. Log at the right level (debug for step-by-step tracing, info for state transitions like "sample expanded," warn for recoverable anomalies, error for failures) and always include structured context (pattern ID, site ID, job ID) rather than interpolating those values into a message string, so logs stay queryable.

1.7 Configuration

Validate environment variables against a schema (zod is already a natural fit given it's used for API input validation too) — fail fast with a clear message if config is invalid, and report every missing/invalid variable together in one error rather than failing on the first one found (nobody should have to fix-and-rerun five times to discover five missing env vars one at a time). Don't read process.env.X scattered through business logic; read it once into a typed config object and pass that around or import it from one module.

Scope validation to what a given entry point actually consumes — don't let one monolithic getConfig() gate every process. This project is now a pipeline of independently-runnable, independently-testable stages (packages/pipeline, M6: discover → ingest → verify → estimate → finalize), and a single all-or-nothing config validator defeats that decomposition: a stage needing neither Redis nor a database still fails to boot if getConfig() validates the whole environment at once. This is exactly what happened in M6 — runIngest called the shared getConfig(), which required DATABASE_URL/REDIS_URL that stage never touches; it passed locally because the developer's own .env happened to have everything set, and only failed in CI, where it wasn't. The fix is to compose config from capability-scoped sub-schemas (a dbConfig, a redisConfig, an httpConfig, etc.) and have each entry point — worker process, single pipeline stage, script — validate only the sub-schemas it actually needs, not import one global blob by default. A stage's own tests are the fastest way to notice this is wrong: if a stage's unit tests need environment variables the stage's own code never reads, the config coupling is too wide.

1.8 Immutability and mutation

Default to const. Mark object properties readonly where a type describes something that shouldn't change after construction (most database row types and API response types qualify). Don't mutate function parameters — return a new value instead. This matters more than usual in the sampling code, where accidental shared mutable state between concurrent Piscina workers is a real, hard-to-reproduce bug class.

1.9 Documentation

TSDoc comments on every exported function, class, and type that isn't trivially self-explanatory. Write about why, not what the code already says — // re-hash on expansion so round two is a superset of round one, not a fresh random sample is useful; // hashes the url is not. A comment that asserts a guarantee ("these counts are durable") is a claim, not decoration — if the code doesn't actually make that guarantee under every code path (crash-then-retry included), the comment is a bug in itself; see §1.13's upsertPatterns example.

1.10 Testing

Vitest for unit and integration tests, files named *.test.ts colocated with the code they test. Anything in packages/sampling (confidence intervals, finite-population correction, min-heap sampling, adaptive expansion) needs tests with known statistical answers checked against — this is the part of the system most likely to look correct while being subtly wrong, and least likely to be caught by manual review; validate against independently published reference values, not just the package's own arithmetic re-expressed (M3 caught two wrong hand-computed test expectations this way — a missed FPC shrink and a misquoted published value — that a self-consistent-only test suite would have happily agreed with). Database-touching code should run against a real (throwaway/test) Postgres instance rather than a mocked query layer, since the whole point of the sampling engine is SQL behavior at scale that a mock can't represent — packages/database's integration suite (real Postgres 16) is the model to follow for any package with DB-touching logic.

Mocked-transport tests and real-socket tests catch different bugs — a package needs both, and neither substitutes for the other. packages/http's suite is deliberately, entirely mocked at the transport boundary (a suite that actually opened real connections would reproduce the exact request behavior the rate limiter and circuit breaker exist to prevent) — correct for that package's unit-level concerns (escalation policy, rate limiting, retry logic). But a real socket's lifecycle isn't fully expressible through a mock: M6's probe.ts bug (destroying a real undici response body raised an async AbortError arriving after the probe had already resolved successfully) only surfaced once the pipeline's end-to-end test exercised a real local HTTP server. When a package wraps a real I/O primitive (a socket, a file handle, a stream), keep the mocked unit suite for logic and add at least one test against the real primitive (a real local server, a real throwaway file) specifically for teardown/lifecycle behavior — mocks model the request/response contract, not the resource lifecycle around it.

A structural invariant that's cheap to check and expensive to get wrong belongs in a database constraint, not just a test or an alert — e.g. a CHECK constraint making a degenerate confidence interval (claiming a zero-width interval from a partial sample) literally impossible to write to the table, rather than a monitoring alert that fires after the bad row already exists. Prefer "unwritable" over "alerted on" wherever the invariant can be expressed declaratively.

Tree/graph-shaped and streaming algorithms need an adversarial corpus, not just tidy small fixtures. packages/sitemap's pattern-extraction rewrite (M2, see §1.12 and ADR-0012) shipped correct against small hand-written test cases and still contained three bugs that only a large synthetic corpus modeled on real sitemap shapes surfaced: a partial collapse that made surviving literal sibling nodes unreachable, a bottom-up rebuild that never revisited the subtree it had just merged, and nodes created immediately before a collapse that fingerprinted as leaves and were stranded. Each produced plausible-looking, non-crashing output — exactly the failure mode small tidy fixtures are least likely to catch, because a hand-written test case rarely happens to exercise the specific ordering or edge shape that triggers the bug. Any package doing incremental tree/trie construction, merging, or streaming aggregation should maintain (and keep adversarial, not tidy) a large synthetic corpus test alongside its unit tests, at the scale the feature is actually meant to run at (e.g. the 10M-URL synthetic corpus for packages/sitemap).

A per-package or per-unit test suite passing everywhere is not evidence the assembled system is correct — budget for an end-to-end pass, and expect it to earn its keep. Every package involved in the M6 pipeline had its own green test suite (packages/http, packages/database, packages/sampling, packages/sitemap) before the pipeline's own end-to-end run against a real Postgres and a real local HTTP server found three defects none of those suites could have: the probe.ts teardown bug above, an audit_snapshot.impact_score column typed bigint for a value that's fractional by construction (nothing had ever actually written that column before), and an inverted escalation-cap comparison that only manifests once the cap is wired into a real run rather than exercised in isolation. Treat "does the whole pipeline actually run, on real dependencies, and produce a row that satisfies every constraint" as its own required test, not an assumed consequence of every component test passing — see §1.13 for why this specific failure shape (correct parts, broken whole) keeps recurring.

1.11 Formatting and linting

Biome as the primary linter/formatter, plus a narrow, type-aware ESLint pass limited to @typescript-eslint/no-floating-promises and @typescript-eslint/no-misused-promises (see §1.5 — Biome cannot express these since they require type information). This is the one documented exception to "pick a single tool" — don't add further ESLint rules to that pass without a similar type-information justification, or the exception quietly becomes "running both linters" again. Wire it up as a pre-commit hook (husky + lint-staged) so formatting/lint issues never reach a PR in the first place, rather than relying on CI to catch them after the fact.

1.12 Porting vs. replacing an existing algorithm

"Port the legacy algorithm" is a reasonable default instruction, but it is not a mandate to reproduce a bug faithfully. If validating a ported algorithm against a large, realistic corpus turns up a structural defect in the original — not a porting mistake — replacing it is the right call, provided the replacement is validated against the same corpus and the decision is recorded as an ADR rather than left as an undiscussed departure from "port legacy." The concrete instance (M2, ADR-0012): the legacy pattern-extraction algorithm used a minimum-observation floor of 3 (so the first three URLs through any slot always look 100% distinct, and the algorithm parameterizes on that noise) and one counter per path position shared across the entire site (so a handful of large top-level sections drag unrelated smaller sections into the same pattern). Both defects exist in both the incremental and batch legacy code paths, not just the port. The fix — a prefix trie scoped per path position — was validated against the same corpus and produced patterns that were each an actual coherent family rather than a merge of unrelated ones. Because the output differs from the legacy engine's (by design, and for the better), run a side-by-side comparison against at least one real production site's sitemap before this path replaces the legacy one in production, not just against the synthetic corpus.

1.13 Composition correctness — the recurring defect class in this codebase

Two independently-correct pieces, wired together, are the single most common source of real bugs found in this project so far — more than any individual algorithm defect. Each instance below passed its own unit/integration tests in isolation; each broke only once composed, and none of the individual pieces' tests could have caught it, because the invariant that broke belonged to neither piece alone:

M2 — sampling hash + uniqueness constraint. sample_observation's uniqueness constraint on url_hash (correct as a fast lookup key) combined with the min-heap sampler's smallest-K-hashes selection (correct as a sampling method) to silently drop real observations, because the sampler concentrates retained values in exactly the collision-densest region of the hash space. Neither the hash function nor the sampler was wrong on its own.
M5 — a caller hook + a rate limiter. Composing a caller-supplied hook with the built-in rate limiter silently dropped the caller's hook. Both pieces worked correctly standalone; only their combination broke the platform-wide request-budget accounting the hook existed to provide, and nothing about either piece's own behavior looked wrong from the outside.
M6 — an escalation cap + real pipeline wiring. An escalation-cap comparison that was correct in packages/http's own (mocked) test suite came out inverted once wired into the real pipeline — the exact defect class this section exists to name; found only by the end-to-end run (§1.10), not by either side's own tests.
M6 — a monolithic config validator + a stage that needs less than the whole. getConfig() was individually correct (it does validate the environment correctly, given a complete one), and runIngest was individually correct (it does the right thing with a valid config) — but composing "one stage" with "one config validator that assumes every stage's dependencies" produced a stage that couldn't boot without dependencies it never used. See §1.7.
M6 — an additive-write function + a different write pattern. upsertPatterns is additive by design, written to be called per-file as a streaming pass progresses. A caller that instead accumulates in memory and writes once at the end, while separately marking files as parsed incrementally, creates a window where a crash-then-retry skips already-marked files — and their contribution is now silently and permanently absent from every count, with the run finishing "clean." Neither the writer's additive contract nor the caller's own per-file progress tracking was wrong in isolation; the composition created a durability gap that belonged to neither.

The standing rule: when wiring two independently-tested pieces together — especially across a package boundary, a sync/async boundary, or anywhere one piece's implicit contract (how it expects to be called) meets another's actual calling pattern — write a test for the composition itself, not just for each piece alone. A green suite on both sides of a wire is not evidence the wire is correct. Where practical, make the implicit contract explicit and checkable (a type, a runtime assertion, a test that would fail if the calling pattern changed) rather than leaving it as a comment's claim — an incorrect comment asserting durability is itself a symptom of this defect class (§1.9).

2. PostgreSQL / SQL
2.1 Identifiers

Always snake_case, always lowercase, no exceptions — Postgres folds unquoted identifiers to lowercase anyway, so mixed-case names silently stop working the moment a query forgets to quote them. This means the query layer (Drizzle/Kysely) needs an explicit camelCase-JS ↔ snake_case-SQL mapping at the boundary; don't fight this by trying to keep JS-style names in the database.

Table names: singular nouns (pattern, sample, site, not patterns/samples/sites). This is a real, debated choice (Rails-style pluralization is common too) — singular is picked here because it avoids irregular-plural edge cases entirely and reads naturally in a join (pattern.id = sample.pattern_id, not patterns.id = samples.pattern_id). Foreign keys are always <singular_referenced_table>_id (site_id, pattern_id). Every table gets created_at and updated_at (timestamptz, not timestamp, to avoid timezone ambiguity); soft-deletable tables get a nullable deleted_at. Boolean columns are prefixed is_/has_ (is_verified, has_redirect).

Primary keys: id alone for a non-partitioned table. Exception for partitioned tables: PostgreSQL requires every unique index (including the primary key) on a partitioned table to include the partition key column, so a table partitioned by site_id has primary key (site_id, id), not plain id — this is a database constraint, not a style preference, and it has the side benefit that every child row already carries site_id for partition pruning. This exception is recorded as an ADR (see docs/decisions.md, ADR-0010) — don't rediscover it per table; any new partitioned table gets the same (site_id, id) treatment.

Cross-tenant references need two layers of isolation, not one. Compile-time query scoping (§1.4's opaque Database type) stops an unscoped query from compiling, but it does not by itself stop a row from being written with a site_id that disagrees with a foreign-key-referenced parent's own site_id — a schema-level gap, not a query-level one, and it needs its own proof. Found post-M3: a row could carry one site's site_id while its FK pointed at a different site's parent row, because only the FK column itself was constrained, not the (site_id, id) pair on the referenced side. Closed with UNIQUE (site_id, id) on every partitioned parent plus repointing the child FKs at that composite unique constraint (migration 0002), and isolation.test.ts gained explicit cross-site cases that write a mismatched site_id and assert the database itself rejects it. Any new partitioned table with a tenant-scoped parent needs this same schema-level pairing, verified by its own cross-site test — the compile-time guard alone is not sufficient evidence of isolation.

2.2 Indexes and constraints

Name indexes idx_<table>_<column(s)> (idx_sample_pattern_id), unique constraints uq_<table>_<column(s)>, and foreign key constraints fk_<table>_<referenced_table> — explicit names, never left to the database's auto-generated ones, because auto-generated names make migrations and error messages much harder to read once the schema has hundreds of objects across partitioned tables.

Use CHECK constraints for statistical/data invariants that can be expressed declaratively (see §1.10) — e.g. a sample that didn't cover its full population cannot report a zero-width confidence interval, with an explicit exception for the case where the full population genuinely was counted rather than estimated. This class of constraint is worth the effort to write correctly: it turns what used to be the highest-value alert in the legacy system into something that can't be written to the table in the first place. Watch the column type against the actual formula, not just the vague name of the value. audit_snapshot.impact_score shipped as bigint — a plausible guess from the column's name alone — but the Impact Score is estimate × severity, fractional by construction; the mismatch went unnoticed until the first real run actually wrote a row (M6), because nothing had exercised that write path before. When a column holds a computed value, derive its type from the formula that produces it, and make sure at least one test actually performs that write before considering the column "done."

Never make a non-cryptographic, deliberately-non-uniform hash the target of a uniqueness constraint. sample_observation was originally unique on url_hash (M1) rather than on the URL itself. The hash is FNV-1a truncated to 32 bits — fine for its actual job, feeding the bounded min-heap-by-hash sampler — but a uniqueness constraint on it means two different URLs that happen to collide in 32 bits silently reject one observation as a duplicate of the other. Worse, because the min-heap sampler specifically selects the smallest K hashes seen, the retained sample is exactly the subpopulation of hashes clustered in the narrow low end of the 32-bit space — precisely where collisions are most concentrated, not evenly distributed across the full keyspace. The fix (M2, migration 0001) was to move the uniqueness constraint to the URL itself, the actual identity the table is tracking; the hash stays as a sampling key, never a uniqueness key. Generalize this: a hash chosen for its sampling/bucketing distribution properties is not thereby a safe or sufficient uniqueness key, especially over the exact subset of the hash space the sampling method preferentially selects.

A refusal is not evidence of health. An HTTP 403 (the target blocking the checker, not the checked page failing) must never contribute positive impact/health score — enforced at the database level (M4), not just in application logic, since a crawler-blocking-but-otherwise-broken site would otherwise silently outrank genuinely healthy ones. When a status class represents "we don't actually know," don't let it default into either the healthy or unhealthy bucket at the schema level.

2.3 Query style

No SELECT * in application code — list columns explicitly, so a later ALTER TABLE ADD COLUMN doesn't silently change the shape of every query result. No ORDER BY random() on any table that can grow large — this was a specific, already-identified problem in the sampling engine (see the architecture doc) and the fix (bounded min-heap by hash) applies to any future code that needs a random-ish sample, not just the original instance. Every query is parameterized — string concatenation into SQL is never acceptable, even for internal tooling.

node-postgres returns bigint-typed aggregate results (e.g. sum(...)::bigint) as JavaScript strings, not numbers, to avoid silent precision loss above Number.MAX_SAFE_INTEGER — cast explicitly and deliberately at the query boundary rather than relying on implicit coercion, which will work in small tests and misbehave silently at real scale. Be explicit about NULL ordering (NULLS FIRST/NULLS LAST) in any query where nulls can appear in a sorted/ranked column — Postgres's default (NULLS LAST for ASC, NULLS FIRST for DESC) is easy to get backwards from intuition and easy to leave unspecified until it silently produces a wrong ranking.

Run EXPLAIN ANALYZE on any query touching a table expected to exceed roughly 1M rows before merging it — this project's entire premise is operating at a scale where a missing index or an accidental sequential scan is the difference between milliseconds and minutes.

2.4 Migrations

One logical schema change per migration file. Never edit a migration that has already been merged/shipped — write a new one that alters or corrects it, the same way you'd never rewrite git history that others have already pulled. Prefer migrations that are reversible (a working down) where practical. Pick one migration tool as the source of truth for the schema (Drizzle Kit, matching the query-layer choice for the sampling/sitemap packages) rather than letting two ORMs each maintain their own migration history against the same database — that's a guaranteed way to end up with drift no one notices until it breaks.

Known limitation: Drizzle Kit cannot generate PARTITION BY DDL, so a migration that creates a partitioned table is hand-completed after generation, not purely auto-generated — deleting and regenerating such a migration file produces SQL that still applies cleanly and typechecks, but silently drops the partitioning. Any migration file with hand-completed partition DDL needs: a comment banner saying so, a test asserting the affected tables report relkind = 'p' with the expected partition strategy against a real database, and a test asserting whatever constant lists the partitioned tables in code matches what the database actually reports. Never run an auto-push/sync command (e.g. drizzle-kit push) against a partitioned schema — same silent-unpartitioning failure mode. Revisit this whole workaround if Drizzle ever adds native PARTITION BY support.

2.5 Partitioning and scale

Large per-URL and per-pattern tables are partitioned by site_id from the moment they're created, not retrofitted after data exists — this is both a multi-tenancy isolation measure and a query-performance one (see the architecture doc's Phase 3). Keep transactions short: never make an HTTP call, wait on a queue, or do other slow I/O inside an open database transaction — hold the transaction only for the statements that need atomicity.

3. Repository hygiene

Conventional Commits for every commit message: feat:, fix:, chore:, docs:, refactor:, test:, perf:, optionally scoped (feat(sampling): add finite-population correction). Branch names: feat/<short-description>, fix/<short-description>, or phase-<n>/<short-description> (or phase-<n>/m<milestone>-<short-description> for a numbered milestone within a phase) for work tied directly to a phase in the action plan. PRs should note which phase or open decision (from docs/architecture-review-and-action-plan.md) they relate to, where applicable, and include tests for new logic rather than relying on a follow-up "add tests" PR that tends not to happen. Keep an unrelated large-diff change (a lockfile-rewriting package-manager upgrade, a dependency major-version bump) in its own commit/PR, separate from feature work.

Record a real engineering decision — a tooling choice, a standards exception, a resolved conflict between two docs, a deliberate departure from "port the legacy algorithm" — as an ADR in docs/decisions.md, not only in a commit message or PR description. Commit history is not a substitute for a decision log someone can skim later without archaeology.

A CI workflow's trigger conditions are as much a correctness surface as the checks it runs. A workflow that only triggers on pull_request and push to main never actually runs after a PR merges into develop — meaning every "CI is green" claim up to that point had only ever been checked on the PR's own source branch, never on the branch state everyone actually builds on next. Verify a workflow's trigger conditions directly (not just that a recent run happened to be green) whenever CI's role in the workflow changes, e.g. adding a new long-lived branch.

Confirm a claimed merge/promotion state with a direct check, not a recollection of what was pushed. "Are all branches merged" is answered by git merge-base --is-ancestor <branch> main for each branch (or equivalent), not by remembering the sequence of PRs that were opened — a promotion PR can consolidate several branches' worth of unmerged work into one merge, and the only way to confirm nothing was left behind is to check each ref directly against the target.

4. Tooling summary
Linting/formatting: Biome (primary) + a narrow type-aware ESLint pass for no-floating-promises/no-misused-promises only (§1.11) — wired into a pre-commit hook via husky + lint-staged.
Type checking: tsc --noEmit in CI, strict: true everywhere.
Testing: Vitest, plus large adversarial synthetic-corpus tests for tree/streaming algorithms (§1.10), at least one real-socket/real-primitive test alongside any mocked-transport suite for I/O-wrapping packages (§1.10), and an end-to-end pass against real dependencies for anything assembled from multiple independently-tested packages (§1.10, §1.13).
Schema/config validation: zod, composed from capability-scoped sub-schemas so a given entry point validates only what it consumes (§1.7) — not one global config object imported everywhere by default.
SQL migrations: Drizzle Kit as the single source of truth for schema migrations, with the hand-completed-partition-DDL caveat in §2.4.
Monorepo task configuration (Turborepo): any environment variable a task's code actually reads must be declared in that task's env (or passThroughEnv) list in turbo.json — Turborepo filters undeclared env vars out of a task's environment for cache-correctness reasons, which means an undeclared but load-bearing variable (e.g. DATABASE_URL for a DB integration test task) can be silently absent in CI while a local run "works" off a fallback default that happens to coincide with the intended value. Found in M6: the test task declared no env at all, so CI's real DATABASE_URL was being filtered out and every DB integration test had been passing only because the code's fallback default happened to match the CI service container's connection string — the workflow's configured DATABASE_URL had never actually been exercised. Treat a green DB-integration-test run in CI as unverified until the task's turbo.json entry is checked to confirm the relevant env vars are actually declared, not just present in the workflow YAML.
