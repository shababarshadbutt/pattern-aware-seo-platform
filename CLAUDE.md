docs/DESIGN.md — wins over the architecture/tech-stack doc for anything about UI presentation, motion, or the frontend design-tooling recommendation. When a conflict surfaces, add an ADR recording which side won and why — don't just silently pick one.

What this is

A pattern-aware, sampling-based SEO intelligence platform. It does not crawl every URL on a site. It collapses a sitemap's URLs into a much smaller set of patterns, samples each pattern statistically (with proper confidence intervals, not guesses), and verifies health with targeted HTTP checks — the entire point is auditing a 90M-URL site without making 90M requests. Any change that reintroduces "just crawl everything" thinking is working against the product's actual differentiator.

The core entity model (landed in M1) is organization → site → sitemap_run → sitemap_file → pattern → pattern_population / pattern_sample → sample_observation, plus audit_snapshot and sampling_health. site exists independently of any one audit run — this is the deliberate fix for the legacy tool's design, where the root entity was a one-off session with no memory of a site being audited again later. Trends, regressions, a fleet view across sites, and history to train a model on all depend on site being a durable entity, not an artifact of a single run. Don't reintroduce a run-rooted model even locally in new code. Correction found post-M3: M1's claim that cross-tenant references were structurally unrepresentable was only half true — the compile-time query guard (below) was real, but the schema itself allowed a row to carry one site's site_id while its sitemap_run_id pointed at a different site's run, because only (sitemap_run_id) was constrained, not the pair. Fixed in migration 0002 (UNIQUE (site_id, id) plus five repointed FKs); isolation.test.ts now has explicit cross-site cases proving the hole is shut. Lesson: a compile-time guard on how queries are written doesn't by itself guarantee the schema can't store a cross-tenant reference — both layers need their own proof.

As of M2, single-pass streaming ingestion is real and benchmarked (10,000,000 URLs, 681 MB peak RSS against a 1,536 MB budget, ~41,600 URLs/s, byte-identical resume). Pattern extraction does not faithfully port the legacy algorithm — the legacy algorithm had a real correctness defect (see ADR-0012, and the Non-negotiable rules below) and was replaced with a prefix trie after corpus testing proved the defect out. Don't assume "ported from legacy" describes packages/sitemap's pattern extraction; check docs/decisions.md first.

As of M3, the confidence-math layer is real: Wilson score intervals with finite-population correction, and adaptive sample expansion wired to the min-heap's expansion bounds (see Milestone log below and ADR-0013). Phase 1 (the sampling/population engine) is complete as of M3, aside from the still-open shape/stratum schema question noted under Open decisions in the architecture doc.

As of M4, Phase 2 has started: the Impact Score (severityFor, ADR-0014) is real, with no default severity table in code — a missing argument throws rather than silently shipping a guessed answer. See Milestone log below.

Non-negotiable project rules

These come out of a specific architecture review and its critique (see the action plan doc for the full reasoning) — they are not arbitrary preferences, and deviating from them reintroduces problems that were already identified and fixed once.

No ORDER BY random() for sampling, ever, on tables that can grow large. Use the bounded min-heap-by-hash approach in packages/sampling — implemented and benchmarked at 10M-URL scale as of M2.
Confidence math must use the Wilson score interval with finite-population correction, not a naive normal approximation. This lives in packages/sampling — don't recompute it ad hoc elsewhere. Implemented in M3 (see Milestone log below) — Wilson score interval, finite-population correction, and adaptive sample expansion wired to the min-heap's expansion bounds, validated against published Wilson values rather than the package's own output. That validation process itself found two wrong hand-computed reference expectations (a missed FPC shrink, a misquoted published value) — corrected against the actual math, not the code. A float-epsilon defect at p̂ = 1 (computed upper bound landing fractionally above 1) is now clamped — see the CHECK constraint note below. The degenerate-interval defect (a [0,0] interval falsely implying certainty from a partial sample) is a database-level CHECK constraint, not just an application check, with an n = N exemption for a fully-counted population — see M1 notes below. Confidence-band classification (LOW/approximate/confident) uses two separate threshold pairs, not one, because width-relative-to-estimate and width-relative-to-population bound genuinely different quantities and break in different regimes (ADR-0013) — don't collapse them back into one threshold.
HTTP verification is HEAD-first, GET only on suspicious results, and GET body fetches must be size-capped (soft-404 detection needs the first few KB, not the whole page). Cap how much of a pattern's sample is allowed to escalate to GET before flagging it for manual review instead of continuing. (Same note as above — the body-cap specifics were corrected during M0 verification; defer to docs/decisions.md.) The escalation cap is a policy decision as of M4: a budget against the planned sample size, not a ratio against work already done (a ratio trips on the first probe — one of one is 100% — and would need an arbitrary warm-up floor to be usable). The policy is decided and tested; wiring it into the actual HTTP client is the next milestone (M5) — don't treat the absence of a wired client as the policy being undecided.
A refusal can never carry impact. A 403 is both an HTTP status and a site's explicit refusal — scoring it as an ordinary client error in the Impact Score would rank a crawler-blocking-but-otherwise-healthy site above genuinely broken ones. Enforced at the database level as of M4 (ADR-0014), not just in application code — don't add a code path that lets a refusal status compute a nonzero impact contribution.
Volume can outweigh severity in the Impact Score, deliberately. 50,000 redirect chains outrank 200 gone (410) pages — the score, not the severity class alone, drives triage ranking. This was specifically tested for in M4 after the implementer's own first instinct (":worst finding" = highest severity class) turned out backwards; the test is pinned so this can't silently invert again. Don't "fix" a ranking that looks surprising without checking this rule first.
Never materialize a full URL population in memory or in a single query result. Everything works off streaming passes and pattern/file-level aggregates, not per-URL row sets at the 10M+ scale. M2's benchmark (681 MB peak RSS for 10M URLs) is direct evidence this is holding in practice, not just in intent.
A run that completes without throwing is not necessarily a run that succeeded. A sitemap parse that yields zero URLs from an accepted file is indistinguishable from a legitimately empty site unless it's flagged explicitly (an HTML error page parses as valid XML — this bit M2). Any code path that can "succeed" with an empty or suspicious result must signal that explicitly (structured warn log at minimum) rather than looking identical to an ordinary success. See docs/CODING_STANDARDS.md §1.5. Two more instances found post-M3: a CLI accepting --urls abc silently no-opped instead of failing, and a finalize() claimed idempotency it didn't actually have — both are the same underlying defect class as the M2 empty-run problem, not a new one.
Multi-tenant isolation is a first-class concern, not an afterthought, and has two layers that must each be proven separately. Layer one: unscoped, cross-tenant queries against packages/database are a compile error, not a runtime risk, by construction (opaque Database type + single entry point) — see compile-guards.test.ts. Layer two: the schema itself must not be able to store a cross-tenant reference regardless of how it's queried — every table referencing a tenant-scoped parent constrains (site_id, parent_id) as a pair, not the parent id alone (see the cross-tenant FK correction above; migration 0002 closed the gap for sitemap_run references, recorded via isolation.test.ts's cross-site cases). Large per-URL/per-pattern tables are partitioned by site_id from schema creation (as of M1, six tables), not retrofitted later. BullMQ queues and Redis keys are namespaced per site/tier so one site's job volume can't starve another's — this piece (queue/Redis namespacing, connection-pool budgeting) is still pending, not yet built.
Query layer split: use Drizzle or Kysely (not Prisma) for anything in packages/sampling or packages/sitemap — this workload needs hash filtering, window functions, and CTEs close to raw SQL. Prisma is fine for simple CRUD (dashboard/admin, user/site management) if used there, but never for the sampling hot path. Drizzle Kit is the schema migration source of truth, but it cannot generate PARTITION BY DDL — partitioned-table migrations are hand-completed with three verification guards (banner comment, a relkind = 'p' test against a real database, a test asserting a PARTITIONED_TABLES constant matches what the database reports). Never run drizzle-kit push against this schema — see docs/CODING_STANDARDS.md §2.4. Also watch Drizzle Kit's constraint-ordering behavior on non-partition migrations: migration 0002 had keys emitted before the constraint they target, failing on the first ADD — hand-reorder when this happens rather than assuming generated migration SQL applies in a safe order by default.
Never make a uniqueness constraint out of a hash chosen for its sampling distribution properties. sample_observation was originally unique on the 32-bit FNV-1a url_hash, which — combined with the min-heap sampler specifically retaining the smallest hashes — clustered collisions in exactly the retained sample and silently dropped real observations. Fixed in M2 (migration 0001) by moving uniqueness to the URL. See docs/CODING_STANDARDS.md §2.2 before adding any new uniqueness constraint on a hash column.
"Port the legacy algorithm" does not mean reproduce a proven defect. If a large adversarial corpus test (not a small hand-written fixture) demonstrates the legacy algorithm is structurally wrong, replacing it is correct — provided the replacement is validated against the same corpus and recorded as an ADR. See docs/CODING_STANDARDS.md §1.12 and ADR-0012 (the M2 pattern-extraction rewrite). Don't treat this as license to casually diverge from legacy elsewhere — it applies specifically when a defect is demonstrated, not by default.
ML work lives in ml-service/ (Python), never inlined into the Node platform. The Node/TypeScript core stays as-is; ml-service/ reads features from the same Postgres database and serves predictions over a small internal endpoint or writes them back on a schedule.
Don't reach for: NestJS, Lambda for the main workers, MongoDB, SQS in front of BullMQ, or EKS — all considered and rejected for this workload in the architecture doc. Revisit only if a concrete gap shows up in practice, not speculatively.
Don't add a new PopulationProfile-style entity (or similar) without first checking whether pattern_shape_rules, structureClusters, or shapeStrata already cover it — this is still an open decision. M1's pattern_population/pattern_sample schema addresses the population/sample storage question but has not been confirmed as resolving the shape/stratum distinction specifically, and none of M2, M3, or M4 have touched this question — don't assume it's settled without checking the architecture doc's open-decisions section.
Don't guess severity weights, escalation policy numbers, or any other business-facing constant. The Impact Score's severity table (ADR-0014) was explicitly ratified by the project owner rather than shipped as a plausible-looking default, and the code enforces this structurally — severityFor throws without an explicit table rather than falling back to one. Apply the same pattern to any future business-facing constant: no silent default, surface the decision.
Coding standards (see docs/CODING_STANDARDS.md for full detail)

The essentials an agent must not violate by default:

TypeScript strict mode everywhere; no any — use unknown and narrow it.
Named exports only; no default exports.
ESM only ("type": "module") — no require() in new code.
All async code uses async/await; no unhandled/floating promises (enforced via a type-aware lint rule — see docs/decisions.md for which tool covers this).
Structured logging (pino) — no stray console.log in application code, only in one-off scripts.
Every table, column, and index name is snake_case; every foreign key is <singular_table>_id; every table has created_at/updated_at. Partitioned tables use a composite primary key (site_id, id), not plain id — Postgres requires the partition key in any unique index or PK on a partitioned table (see ADR-0010). Any FK to a tenant-scoped table constrains (site_id, parent_id) as a pair, not the parent id alone (see the cross-tenant FK fix, migration 0002) — this is now standard practice, not a one-off correction.
All SQL is parameterized — no string-concatenated queries, ever.
Every exported function that isn't trivial gets a short TSDoc comment explaining why, not a restatement of the signature.
Environment variables are validated once at startup via a schema (zod), fail-fast, reporting all missing/invalid vars together rather than one at a time — never read scattered process.env.X calls through business logic. Keep .env.example itself passing that same validation — a template value that fails its own schema (e.g. an empty required secret) breaks onboarding on the first command a new contributor runs.
Statistical invariants that must never silently hold a wrong value (e.g. the degenerate-interval case above) get a database CHECK constraint, not just an application-level assertion — "unwritable" beats "alerted on." The same applies to business invariants like "a refusal never carries impact" (ADR-0014) — enforce in the schema where the invariant can be expressed declaratively, not only in application logic.
Tree/trie/streaming-aggregation code (packages/sitemap is the model) needs a large adversarial synthetic corpus test, not just small hand-written fixtures — three real bugs in M2, plus a memory-cap undercount in PatternTrie.merge() found post-M3, only surfaced at corpus/integration scale.
Never put a uniqueness constraint on a hash column chosen for sampling/bucketing distribution, not collision resistance.
Statistical code validated against reference values should check those values against an external, published source, not just re-derive them from the same reasoning as the implementation — M3 found two of its own hand-computed reference expectations were wrong, not the code being tested.
Don't trust a driver's declared return type over its actual runtime behavior for numeric aggregates — sum(...)::bigint comes back as a JS string from node-postgres/pg, not a number (BIGINT exceeds safe-integer range, so the driver won't silently coerce it). Cast/parse explicitly at the query boundary; don't assume TypeScript's inferred type reflects what the driver actually returns.
Workflow expectations
Check which Phase (0–5) a task belongs to in the action plan before starting; Phase 1 (sampling/population engine) work shouldn't get blocked on Phase 5 (SEO audit UI) polish, and vice versa.
When a change touches a decision the action plan marks open, say so explicitly rather than picking an answer silently.
Update docs/architecture-review-and-action-plan.md when a real architectural decision gets made or changed — it's meant to stay current, not freeze as a one-time snapshot. Prefer amending with dated findings over silently rewriting original text, so there's a record of what changed and why (this is what M0 through M4, plus the post-M3 hardening pass, all did).
Record tooling/version/schema/algorithm decisions as ADRs in docs/decisions.md rather than only in a commit message or PR description — commit history isn't a substitute for a decision log someone can skim later.
Never commit .env, credentials, or AWS/SFTP keys. .env.example documents what's needed; real values stay local or in Secrets Manager.
New logic in packages/sampling (confidence intervals, sampling algorithms, statistical decisions) needs tests — this is the part of the system a wrong-but-plausible-looking answer would be most costly, and it's also the part hardest to eyeball-review. The same standard applies to anything asserting tenant isolation (e.g. compile-guards.test.ts, isolation.test.ts) — these are correctness-critical, not incidental.
Before merging a schema migration, confirm it doesn't fight a native/local install shadowing a Docker service on the same default port (this bit M1 with Postgres on Windows) — use the POSTGRES_PORT/REDIS_PORT overrides rather than assuming the default port is actually reaching the container.
Before replacing a ported algorithm because a corpus test found a defect in the original, validate the replacement against the same corpus and write the ADR (see ADR-0012) — don't just swap it in silently.
Before merging any PR, confirm the actual GitHub Actions run went green — reading the job logs for anything that touches a service container (e.g. Postgres), not just the pass/fail badge, since a green badge on a silently-skipped suite is worse than a red one. Also confirm the workflow actually triggers on the branch you think it does — the post-M3 hardening pass found the workflow only ran on main and pull_request, so merged PRs produced no run at all on develop; every earlier "CI green" claim had only ever been checked on the PR's source branch, never after the merge actually landed. Add the push trigger for every long-lived branch that receives merges, not just main. Automated review comments (e.g. Copilot Code Review, enabled on this repo) are useful signal but are not a substitute for human review — in the post-M3 pass, nine Copilot findings were checked individually and all nine turned out real, including the cross-tenant FK gap above; don't assume that hit rate generalizes, but don't dismiss the tool either.
Git conventions
Conventional Commits: feat:, fix:, chore:, docs:, refactor:, test:, perf:.
Branch names: feat/<short-description>, fix/<short-description>, or phase-<n>/<short-description> (or phase-<n>/m<milestone>-<short-description>) for work tied directly to an action-plan phase. Each new milestone branches off the tip of the previous one (M0 → M1 → M2 → M3 → M4 → ...), and PRs stack the same way (each PR's base is the branch it was cut from) rather than every branch targeting develop directly — one reviewable diff per milestone instead of overlapping ones. Merge bottom-up so everything lands on develop in order. A cross-cutting fix that touches multiple already-merged milestones (e.g. the post-M3 Copilot-findings pass) can be consolidated into one PR directly against develop instead of threading it through the original stack, once that stack is already merged.
Don't push directly to main once more than one person is working in this repo — open a PR, even a small one. develop is kept as the integration branch (team decision, 2026-09-02) rather than merging milestone stacks straight to main; main is promoted via its own develop → main PR once develop holds a verified set of milestones. As of the post-M3 pass, develop is at b5a5998, six commits ahead of main and CI-verified on develop itself (not just on the PR branches) — promotion to main is a deliberate, separate call, not automatic once develop is green.
Keep an unrelated large-diff change (a lockfile-rewriting package-manager upgrade, a dependency major-version bump) in its own commit/PR, separate from feature work — makes both easier to review and to revert independently.
Open PRs (don't just push branches) and confirm CI actually runs green in GitHub's environment, not just locally — a passing local run doesn't confirm the CI service containers (e.g. the Postgres service container M1 added) are configured correctly in the real environment, and confirm CI actually triggers on develop after a merge, not only on the PR branch (see the Workflow expectations note above). (A similarly-named but unrelated repo, shababarshadbutt/seo-platform — the legacy Sitemap_Migration engine — was visible to the token and was correctly identified as a trap, not the target.) Fixed by scoping the PAT correctly. The M0–M3 stack (PRs #1–#4) plus a consolidated post-review fix (PR #5) are merged bottom-up into develop, CI verified green with the job logs read directly (not just the badge) — including isolation.test.ts now covering 8 tests, cross-site cases included, against a real, freshly created and dropped Postgres 16 database.
